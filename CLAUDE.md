# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A marketing site for **Typ od Wnętrz**, an interior-design studio (Wrocław & online): a long single-page `index.html` plus one subpage, `portfolio.html`. Plain static HTML/CSS/vanilla JS - **no build step, no framework, no package.json, no tests**. All UI copy is in Polish; keep it that way.

## Running locally

Serve the folder over HTTP (not `file://`) - `image-slot.js` fetches a sidecar JSON at load, which fails on the file protocol:

```bash
# -d needs an ABSOLUTE path - `-d .` fails with "server config failed: Path is not absolute"
java -m jdk.httpserver -b 127.0.0.1 -p 8000 -d "C:\Users\Miacus\IdeaProjects\typ-od-wnetrz"
# then open http://localhost:8000
```

Do **not** use Python to serve this project — stick to the Java toolchain.

There is nothing to build, lint, or test. To deploy, publish the repo root as static files.

## Architecture

**Data-driven rendering.** `index.html` ships mostly empty section shells with mount-point IDs (`#pfGrid`, `#offerGrid`, `#types`, `#procGrid`, `#timeline`, `#revTrack`, `#csList`, `#faqList`, …). At runtime `app.js` reads global data objects and injects HTML via template strings. To change site *content*, edit the `data/*.js` files - not `index.html`.

**Portfolio subpage** (`portfolio.html` + `portfolio.js`). A photo wall showing **one room type at a time**: beige page-head panel, a row of chips (`Kuchnie / Łazienki / Salony / Sypialnie / Pokoje dziecięce / Gabinety / Komunikacja / Hole`), and below it the single selected section. All seven sections are rendered into the DOM; the chips switch which one is visible, like tabs. **There is no "Wszystkie" chip on purpose** - it would mean the ~20 000 px page this replaced; one category is ~4 700 px. The selection writes itself into the address (`portfolio.html#lazienki`, via `replaceState` so Back still leaves the page in one press), and a `#slug` in the URL selects that category on entry - that is how the home page tiles arrive.
Each section shows **12 photos and a "Pokaż wszystkie N zdjęć" button**; the rest are already in the HTML but hidden with `display:none` (`.pfp__shot.is-extra`), which is what keeps the browser from fetching them - opening the page costs ~1,3 MB, not 400 files. It does **not** read `window.PROJECTS` and does not use `<image-slot>`: the gallery is plain `<img loading="lazy">`.

**Portfolio photos are a generated pipeline. Never hand-edit `data/gallery.js`.**
- `images/portfolio/<room>/` - the ORIGINALS as delivered (PNG, 2-5 MB each, ~1,4 GB). **Git-ignored on purpose** (`.gitignore`): source material that lives on disk, is never committed and is never served. Keep a backup outside the project - git is not one. Only `images/portfolio-web/` ships.
- `java tools/GalleryOptimize.java` - writes web copies to `images/portfolio-web/<room>/<name>.webp` (long edge 1400 px, q90: 1,4 GB → 52 MB). Originals untouched, already-converted files skipped, so re-running after adding photos only does the new ones. It also deletes copies that no longer have an original (and the old `.jpg` set), so a renamed photo does not leave its predecessor on the server.
- **It shells out to ffmpeg** (`winget install Gyan.FFmpeg`), because stock Java cannot *write* WebP - ImageIO has no encoder for it. The tool finds ffmpeg in `PATH`, in `%FFMPEG%`, or in the winget package folder, and says so if it finds none.
- **Why WebP q90 and not JPEG:** measured, not assumed. SSIM against an uncompressed reference, on three portfolio frames: JPEG q82 gave 0,9733 / 0,9810 / 0,9829 at 196/152/176 kB; WebP q90 gave 0,9900 / 0,9905 / 0,9920 at 196/124/148 kB. Same or smaller file, visibly more detail - so going below q90 to save a few kB trades away exactly what this site is selling.
- `java tools/GalleryIndex.java` - regenerates `data/gallery.js` (`window.GALLERY`): per category `key/cat/slug/alt/dir/photos[{f,w,h}]`. It reads the web folder when it exists, otherwise the originals. **Dimensions come from the file headers here** so the page knows every frame's shape before downloading it (`width`/`height` on `<img>` = no layout shift, and no measuring with `new Image()`, which at 395 files would mean downloading all of them). For WebP that header is read by hand in `webpSize()` (RIFF + `VP8 `/`VP8L`/`VP8X`) - ImageIO cannot *read* the format either, and pulling in a library for two integers would be a poor trade.
- **After adding or removing photos, run both, in that order.** The room→category mapping (Polish label, anchor slug, `alt` phrase) lives in `ROOMS` at the top of `GalleryIndex.java`.
- Photo order is not alphabetical: file names are `N.jpg` / `N(2).jpg` / `NA.jpg`, i.e. one room shot several times, so covers (one per room) come first and the remaining shots follow. That is why the first 12 tiles are 12 different interiors.

Categories: the subpage builds its chips from `window.GALLERY` (7 room types, Gabinety included) and always has exactly one of them active. The home page has its own shorter list in `window.PROJECT_CATEGORIES` (6) because `#pfGrid` shows one curated tile per category from `images/home-images/` and a seventh tile would break its 3-per-row grid. When you change either list, also update the prose that lists room types - the portfolio lead, `portfolio.html`'s meta/OG descriptions, and `knowsAbout` in the home page JSON-LD.
On the home page `#pfGrid` still shows **one tile per PHOTO, not per project**, using the `orient` field from `window.PROJECTS`; `app.js` interleaves tall/wide because the 12-column grid only closes a row as tall+wide or 3x tall, and adds `.is-sparse` when a filtered view has fewer than three tiles. Those tiles link to `portfolio.html#<catSlug>` - the **category** section, not a project (the subpage has no per-project pages); `catSlug` in `data/projects.js` must match a `slug` in `data/gallery.js`.
The subpage gallery is CSS `columns` (3 / 2 below 900 px), not a grid: with hundreds of photos in mixed proportions a row-based grid would either crop them or leave holes. Nothing is cropped - each frame keeps its own shape.
Clicking a tile opens a **lightbox** (`.lb`, built once by `portfolio.js`, appended to `<body>`). It is **scoped to one section**: the arrows walk that category's photos only, wrapping at the ends, and the counter reads `4 / 50`. It does walk photos the grid has not revealed yet, so the whole category can also be browsed there without pressing "pokaż wszystkie". Esc closes, ←/→ navigate, Tab cycles the three buttons (it is a modal), focus returns to the tile that opened it, and `body.lb-open` locks background scrolling. `.lb[hidden] { display: none }` is **load-bearing**: the author `display: grid` overrides the browser's built-in `[hidden]` rule, so without it the overlay stayed on screen after closing, showing a broken-image icon.
`portfolio.js` is deliberately separate from `app.js`: the subpage has no hero, calculator or contact form, and `app.js` would throw without those nodes in the DOM, so `portfolio.js` re-implements only header/menu/reveal. The category switch **hides** sections (`[hidden]`) instead of re-rendering, so an expanded gallery stays expanded when you come back to it and nothing is re-downloaded. `<body class="page-sub">` forces the light header from the first paint (no dark hero underneath it).

**Scrolling on this page has three rules, each of them learned the hard way:**
- **`behavior: "instant"`, never `"auto"`.** `html` has `scroll-behavior: smooth`, and `"auto"` hands the decision to CSS: a jump becomes a multi-second animation that the next call restarts, so landing on `#kategoria` from a link never arrived at all.
- **Corrections run synchronously, not in `requestAnimationFrame`.** rAF does not fire while the tab is not painting (same trap as `IntersectionObserver` here and in `samples.js`), so an rAF-wrapped scroll can simply never happen. Reading `getBoundingClientRect()` after the class change already forces the fresh layout, so a synchronous measurement is correct.
- **`#pfpList` has `overflow-anchor: none`.** Chrome's scroll anchoring corrects the scroll position by itself when content above the viewport disappears (collapsing a gallery, switching category) and overwrites whatever the script just set.

**Sample-documentation subpage** (`przykladowy-projekt.html` + `samples.js`). Shows what the client gets at the end: the real PDFs from `images/pdf/`, listed in `window.SAMPLES` (`data/samples.js`) with `title`, `scope`, `note`. PDF pages render to `<canvas>` via PDF.js pinned at 3.11.174 from cdnjs — library and worker must be the same release. Image files (`.jpg`/`.png`/…) skip PDF.js and go in as `<img>`. Those files are **public**: anything with a client name, address, phone or contractor data must not land there. The link to this page sits right under the offer tiles (`#offerSamples`) and `app.js` renders it **only when `window.SAMPLES` is non-empty**, so an empty list never produces a link into an empty page — which is why `index.html` also loads `data/samples.js`.
The page opens with a **schedule** built from `window.SCHEDULE_SAMPLE` — real dates from one project, set as text (not the original screenshot) so it is selectable, readable by screen readers and indexable. Each row carries `who` (`"Ja"` / `"Ty"`), which is the point of that table: the deadlines bind both sides. A multi-page PDF shows only the first `maxPages` pages (default 3) plus a link to the whole file — the last page of a long document is usually a quarter full and left a blank sheet the size of the screen right above the footer.
Loading is deliberately **not** `IntersectionObserver`-based: the observer only fires while the tab is painting, so a page opened in a background tab could sit on „Ładuję podgląd…" forever. A scroll/position check does the same job predictably (same reasoning as the reveal fallback in `app.js`). Note that `page.render()` itself uses `requestAnimationFrame` internally, so in a background tab the render finishes only once the tab is shown — that is fine, but it makes the viewer impossible to verify in an automated/headless tab.

**Script load order matters** (see bottom of `index.html`): `image-slot.js` → `data/projects.js` → `data/offer.js` → `data/content.js` → `data/samples.js` → `app.js`. On `portfolio.html` it is shorter and uses neither `image-slot.js` nor `data/projects.js`: `data/gallery.js` (generated) → `portfolio.js`; on `przykladowy-projekt.html`: PDF.js (CDN) → `data/samples.js` → `samples.js`. The data files assign plain globals (`window.PROJECTS`, `window.OFFER_TYPES`, `window.PRICING`, `window.PROCESS_STEPS`, `window.TIMELINE`, `window.REVIEWS`, `window.CASE_STUDIES`, `window.FAQ`, `window.PROJECT_CATEGORIES`, `window.SAMPLES`; `window.GALLERY` only on the portfolio subpage), and `app.js` consumes them, so app.js must load last.

**Single source of truth for pricing.** `window.PRICING` in `data/offer.js` is *derived* from `OFFER_TYPES` (`perType` is built from each type's `price`). The quote calculator in `app.js` (`compute()`/`render()`) reads only `PRICING` - area × zł/m², then volume `discounts` by min m², then optional `rushSurcharge`, with `minArea` below which it shows "wycena indywidualna". Changing a type's price in `OFFER_TYPES` automatically updates the offer grid, the type selector, and the calculator together. Don't hardcode prices elsewhere.

**`<image-slot>`** (`image-slot.js`) is a self-contained custom element for user-fillable image placeholders, built for the "omelette" runtime: drops persist to a `.image-slots.state.json` sidecar via `window.omelette.writeFile`. Outside that runtime it's **read-only** (shows the placeholder caption). Each slot needs a unique `id`; portfolio/case-study slot ids come from the `slot` field in the data files. Treat this file as a vendored dependency - avoid editing it.

**`app.js` also owns** all interactions: scroll-reveal via `IntersectionObserver` (with a scroll/timeout fallback so content is never left hidden), header glass-on-scroll, mobile menu, hero parallax, smooth anchor scroll, portfolio category filter, reviews slider, FAQ accordion, and the contact form. The contact form posts to **Formspree** via `fetch` — the endpoint lives in one constant, `FORMSPREE_ENDPOINT`, at the top of the contact block in `app.js`, and is **live**: submissions really are sent, and reach `typodwnetrz@gmail.com`. Don't submit the form while testing unless you mean to send a real message. The HTML keeps `action=""` on purpose so the address stays in that one constant; `app.js` fills the attribute in at runtime. The honeypot field is Formspree's `_gotcha`. The form can attach the current calculator estimate to the message.

## Conventions

- **Dashes: `–` (en dash / półpauza), never `-`.** In Polish copy a sentence dash and a range are both `–`, surrounded by spaces (`Apartament – Stare Miasto`, `1–2 dni`). This is not just correctness: Cormorant Garamond's hyphen glyph is a short, slanted tick sitting near cap-height, and at display sizes it reads as a typo. The plain hyphen stays only inside compounds (`e-mail`), slugs and URLs (`#o-mnie`). **Never sweep this with a blind find-and-replace over the JS** - ` - ` there is also the minus operator (`scrollY - 70`, `length - 1`); change only the visible strings.
- The theme is **hard-locked to light** - the inline script in `<head>` forces `data-theme="light"` and ignores `?theme=dark` / stored prefs. There is no dark mode to maintain - the `html[data-theme="dark"]` block was deleted from `styles.css`, so a stray `data-theme="dark"` would now change nothing.
- Pricing numbers that appear in prose (not just in the offer grid or the calculator) are INJECTED from `window.PRICING`, never typed into `index.html`: `#rushPct` carries the rush surcharge, `#discFrom` the lowest volume-discount threshold. The number in the markup is only a fallback for when JS fails - keep it correct, but change the real value in `data/offer.js`.
- Cache-bust when editing shared assets by bumping the query version wherever it is referenced (`styles.css?v=…`, `app.js?v=…`, `portfolio.js?v=…`). The `data/*.js` files carry visible copy, so they are versioned too. `styles.css` is loaded by BOTH `index.html` and `portfolio.html` - bump it in both, or one page keeps serving the stale sheet. Note the HTML files themselves are **not** versioned, so browsers cache them — hard-refresh when their markup changes.
- Data-file header comments reference an eventual Next.js migration (`data/projects.ts`, etc.); the current site is the vanilla prototype of that.
- The contact address is `typodwnetrz@gmail.com`, written as plain `mailto:` links in three places (mobile menu, contact section, footer). Cloudflare may re-obfuscate them on serve (`__cf_email__` / `/cdn-cgi/l/email-protection`) and injects its own decode script — that markup is expected in production, not broken. Keep the source plain.
- The hero background is a looping `<video>` (`images/hero-video.mp4`), driven by `app.js`: pauses off-screen, retries blocked autoplay on first interaction, freezes on frame one under `prefers-reduced-motion`.
- **The H.264 hero files are never re-encoded.** `images/hero-video.mp4` (2560×1440 @ 17,75 Mb/s) and `images/hero-video-phone-resolution.mp4` (720×1280) still carry their original bitstream. They have only been remuxed: the AAC track was dropped (the element is `muted` + `aria-hidden`, so it was ~0,5 MB nobody could ever hear) and `-movflags +faststart` moved the `moov` atom to the front - it used to sit at the end, which forced the browser to fetch nearly all 26 MB before the first frame could show. Proof it is bit-identical: `ffmpeg -i file -map 0:v -f md5 -` gives the same digest before and after. If you ever touch these two files, use `-c:v copy` - anything else is a re-encode.
- **Four hero files, exactly one downloaded.** Alongside the H.264 pair sit AV1 copies (`-av1.mp4`, SVT-AV1 preset 3 CRF 18 tune=0): 25,90 → **2,95 MB** on desktop, 7,46 → **1,35 MB** on phone, VMAF 97,2 / 97,8. The inline script under `<video>` picks on two axes - screen (phone vs desktop) and codec (`canPlayType` on the AV1 string) - and assigns a single `src`. A browser that does not know AV1 gets the untouched H.264 file, so the fallback quality is exactly what it always was. **The AV1 level differs per file** (5.0 desktop = `av01.0.12M.08`, 3.1 phone = `av01.0.05M.08`), so the script asks about the file it actually intends to fetch. Re-encoding either AV1 file means re-checking that string with `ffprobe`.
- **Images are WebP; `og-image.jpg` is the one deliberate exception.** Facebook, LinkedIn and WhatsApp do not reliably render WebP link previews, so the Open Graph image stays JPEG (1200×630, ~144 kB, at the repo ROOT because the tags point at `https://typodwnetrz.pl/og-image.jpg`). All three pages declare `og:image:width/height/alt` next to it.
- **Site photos ship only as `.webp`; their sources are git-ignored.** `images/home-images/*.webp` (q95, 1600×2000 - they are the home page's showcase, so they get a higher setting than the gallery), `images/about-me.webp` and `images/detal-photo.webp`. The PNG/JPG they were made from sit next to them on disk but are `.gitignore`d, exactly like `images/portfolio/` - the six home PNGs alone were 24 MB per visit. `screenshots/` is ignored for the same reason: never linked from any page, 14 MB, and it holds the full-resolution original of `about-me` (4672×7008). As with the portfolio originals: **keep a backup outside the project, git is not one.**
- SEO surfaces (`sitemap.xml`, `robots.txt`, canonical/OG/JSON-LD in `<head>`) hardcode the production domain `typodwnetrz.pl`.
